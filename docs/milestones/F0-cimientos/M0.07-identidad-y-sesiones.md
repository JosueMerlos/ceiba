## Objetivo

Un usuario inicia sesión con correo y contraseña, obtiene una cookie `httpOnly` respaldada en BD y puede cerrar la sesión actual o todas. Toda ruta exige sesión salvo la allowlist. Las mutaciones exigen token CSRF y un `Origin` válido.

## Contexto

- Se construye **sobre** tenancy (M0.05): el usuario es global y la pertenencia a organizaciones llega en M0.08 con los memberships.
- Base: el generador de autenticación de Rails 8, movido a `platform/identity` y adaptado.

## Alcance

**Incluye**

- Pack `platform/identity`: `User` (global, no tenant: `email citext unique`, `password_digest`, `full_name`), `Session` en BD.
- `POST /api/v1/auth/login`, `DELETE /api/v1/auth/logout`, `DELETE /api/v1/auth/sessions` (todas), `GET /api/v1/auth/session`.
- Cookie con los flags de [11](../../architecture/11-security.md); expiración por inactividad (12 h) y absoluta (7 días); rotación al login.
- `authenticate!` deny-by-default en el controlador base; `skip_authentication!` explícito y comentado.
- CSRF: token + validación de `Origin`.
- Contraseña mínima de 12 caracteres (HIBP llega en M4.02).
- Respuesta de login idéntica con correo inexistente o con contraseña incorrecta.
- `Principal::User` mínimo (los permisos llegan en M0.08).

**No incluye**

- Memberships, selector de contexto y `/me` completo → M0.08/M0.09. 2FA, bloqueo progresivo, HIBP y reset de contraseña → M4.02. Invitaciones → M4.01. Auditoría de login → se conecta en M0.11.

## Criterios de aceptación

1. **Dado** credenciales válidas, **cuando** se hace login, **entonces** se recibe una cookie `HttpOnly`, `Secure` (en prod), `SameSite=Lax`, y existe una fila en `sessions` con el **digest** del token, no el token en claro.
2. **Dado** una sesión válida, **cuando** se llama a `DELETE /auth/sessions`, **entonces** todas las sesiones del usuario quedan revocadas y la cookie de otro navegador recibe `401`.
3. **Dado** 12 h sin actividad, **cuando** se usa la cookie, **entonces** se recibe `401`.
4. **Dado** cualquier ruta nueva sin `skip_authentication!`, **cuando** se llama sin sesión, **entonces** se recibe `401` (el spec que recorre las rutas lo verifica).
5. **Dado** una mutación con sesión válida pero sin el token CSRF, **cuando** se envía, **entonces** se recibe `403`.
6. **Dado** un correo inexistente y otro existente con contraseña errónea, **cuando** se intenta el login, **entonces** ambas respuestas son idénticas en status y cuerpo.
7. **Dado** un login correcto, **cuando** se compara el token de la cookie con el de antes del login, **entonces** es distinto (se rota).

### Qué se hizo

- **Pack `platform/identity`** (`bin/rails g pack platform/identity`): `Identity::User` (global, no tenant: `email citext` único normalizado, `password_digest`, `full_name`; `has_secure_password`, bcrypt 3.1.22 fijado, mínimo 12) e `Identity::Session` (`token_digest` SHA-256 único, `ip inet`, `user_agent`, `last_seen_at`, `expires_at`, `revoked_at`). Migraciones `20261108210000_create_users` y `20261108210100_create_sessions`.
- **API pública** (`app/public`): `Identity::Authenticate` (login con `authenticate_by`, rotación), `Identity::CurrentSession` (resolución del token, CSRF, revocación), `Identity::ProvisionUser` (seeds), `Identity::Principal::User` y los errores de dominio. Spec que fija ese conjunto.
- **Endpoints** `POST /auth/login`, `GET /auth/session`, `DELETE /auth/logout`, `DELETE /auth/sessions` (rutas del pack con `draw(:identity)`), con rswag, `cookieAuth` y contrato `v1.yaml` + `schema.d.ts` regenerados sin drift.
- **`Api::Authentication`** en `Api::BaseController`: `authenticate!` deny-by-default, `skip_authentication!` explícito (solo el login), `Current.session`/`Current.principal`. Spec que recorre TODAS las rutas del router. **`Api::SessionCookie`**: nombre y atributos de la cookie en un solo sitio. `config/initializers/authentication.rb`: middleware `ActionDispatch::Cookies`, `secure_cookies`, y `active_storage.draw_routes = false`.
- **CSRF:** token HMAC ligado a la sesión en `X-CSRF-Token` + validación de `Origin`/`Referer` en toda mutación.
- **Seeds:** un usuario por organización de demo (`rosa@barberia-guegu.ceiba.test`, `luis@salud-estilo.ceiba.test`), idempotente, como `app_user`, por la API pública de identity.
- Docs: [11](../../architecture/11-security.md) (reescritas las secciones de sesiones y CSRF, deny-by-default y allowlist, contraseñas de demo, checklist), [07](../../architecture/07-api-contract.md), [02](../../architecture/02-modular-monolith.md), [03](../../architecture/03-multi-tenancy.md), [12](../../architecture/12-testing-strategy.md).

### Desvíos de la doc

| Desvío | Motivo |
| --- | --- |
| El token CSRF llega en el cuerpo de `POST /auth/login` y `GET /auth/session`, no desde `/api/v1/me` | `/me` no existe hasta M0.09; una cookie legible no ofrece más seguridad ante XSS y añade superficie. Documentado en [11](../../architecture/11-security.md#csrf-panel) |
| El token CSRF es un HMAC sin estado ligado al id de la sesión, no un valor guardado | Rota con el login, no hay nada que persistir ni limpiar, y no revela el token de la sesión |
| `Identity::Principal::User` (y no `Access::Principal::User`) | El pack `access` y la interfaz `can?` son M0.08; el objeto es solo identidad (`id`, `email`, `full_name`) y M0.08 lo envuelve o reemplaza |
| El endpoint de ejemplo de organizaciones exige sesión pero conserva el flag `open_organization_endpoint` | Autenticar no es autorizar: sin memberships cualquier usuario podría leer cualquier organización. M0.08 lo autoriza y elimina el flag |
| Active Storage no dibuja rutas (`draw_routes = false`) | Sus subidas directas no pasan por `Api::BaseController` y quedaban abiertas sin sesión (las detectó el spec que recorre las rutas). Se reactivan, autenticadas, cuando un hito use archivos |
| Login CSRF: sin token CSRF pero con validación de Origin | Aún no hay sesión de la que derivar un token; Origin + `SameSite=Lax` cubren el ataque |
| Cuerpos "idénticos" salvo `request_id` | El `request_id` es por petición (cabecera `X-Request-Id`); el spec lo fija igual en ambas para comparar el cuerpo completo y además compara sin él |
| Sin `Origin` ni `Referer` no se rechaza por Origin | Curl y clientes no navegador; una mutación autenticada igual exige el token. Un navegador siempre envía `Origin` en una mutación |
| La cookie `Secure`/`__Host-` depende de `config.x.auth.secure_cookies` (= `Rails.env.production?`) | Staging usa `RAILS_ENV=production` (ADR-0013); desarrollo y test son HTTP. Un spec la activa con `https!` |
| Seeds sin vínculo usuario-organización; en producción no se siembran usuarios sin `SEED_DEMO_PASSWORD` | Los memberships llegan con M0.08 (que ampliará el seed); una contraseña de demo pública no puede acabar en un entorno real |

### Limitaciones y pendientes

- **Sin cliente:** `packages/api-client` no envía `X-CSRF-Token` ni recupera el token al arrancar (M0.12).
- **Memberships/permisos:** el principal solo tiene identidad; el endpoint de organizaciones sigue bajo flag hasta M0.08; los usuarios de demo no están ligados a su organización.
- **Sin rate limiting ni bloqueo progresivo** (M0.13/M4.02) y **sin auditoría de login** (M0.11); `request.remote_ip` detrás del proxy se verifica en M0.13.
- **Limpieza de sesiones** vencidas o revocadas: no hay job (la tabla crece); se atiende cuando haya un hito de mantenimiento. El índice por `user_id` cubre "revocar todas".
- **Coordinación con M0.10 (paralelo):** ambos hitos tocan `db/structure.sql`, `Gemfile.lock` y `.rubocop.yml`; las migraciones de identity son `20261108210000` y `20261108210100` (renumeradas al rebasar sobre M0.10, que usa `20261108200000`/`200100`).
- **Pendiente de verificar con el remoto:** que el job `api-contract` y `backend-test` pasen en GitHub Actions con la versión de `bcrypt` compilada en el runner.
