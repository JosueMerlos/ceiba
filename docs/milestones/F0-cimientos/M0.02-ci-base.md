## Objetivo

Todo PR a `main` ejecuta automáticamente lint, tests y auditorías de seguridad de backend y frontend, y **no se puede mergear** si algo falla.

## Contexto

- TDD estricto exige un runner confiable desde el primer test.
- Las herramientas de seguridad (brakeman, bundler-audit) son baratas al inicio y caras de introducir con deuda acumulada.
- Packwerk, OpenAPI y strong_migrations se suman a este pipeline en sus propios hitos (M0.03, M0.06, M0.04).

## Alcance

**Incluye**

- RSpec en el backend (reemplaza el test temporal de M0.01), FactoryBot, configuración base.
- RuboCop (rubocop-rails, rubocop-rspec) con configuración inicial.
- brakeman, bundler-audit.
- Frontend: ESLint, Prettier, `tsc --noEmit`, Vitest (un test trivial por app), `pnpm audit --audit-level=high`.
- Workflow de GitHub Actions con servicios PostgreSQL 18 y Redis, caché de gems y del store de pnpm.
- Protección de la rama `main`; plantilla de PR; validación de conventional commits en el título del PR.
- Dependabot (mensual) para bundler, npm y GitHub Actions.

**No incluye**

- Packwerk → M0.03. strong_migrations → M0.04. Drift de OpenAPI → M0.06. E2E con Playwright → M0.12.

## Diseño

- Jobs paralelos: `backend-lint`, `backend-test`, `backend-security`, `frontend-lint`, `frontend-test`.
- Mismas versiones que `.tool-versions` / Dockerfiles.
- `bin/ci` local que ejecuta lo mismo que CI (para no depender de empujar para saber si falla).

## Criterios de aceptación

1. **Dado** un PR con un spec de RSpec que falla, **cuando** corre CI, **entonces** el check falla y GitHub impide el merge.
2. **Dado** un PR con un error de tipos en `apps/panel`, **cuando** corre CI, **entonces** falla `frontend-lint`.
3. **Dado** un Gemfile con una gema con vulnerabilidad conocida, **cuando** corre CI, **entonces** falla `backend-security`.
4. **Dado** un PR cuyo título no sigue conventional commits, **cuando** se abre, **entonces** el check de título falla.
5. **Dado** el repo limpio, **cuando** se ejecuta `bin/ci` localmente (dentro de Docker), **entonces** ejecuta los mismos pasos que CI.
6. **Dado** un PR sin cambios de código, **cuando** corre CI completo, **entonces** termina en menos de 8 minutos.

## Definición de terminado

## Notas de cierre

**Rama:** `feat/m0.02-ci-base` (local; sin remoto todavía).

### Qué se hizo

- **RSpec 8.1 + FactoryBot** reemplazan a minitest; `backend/test` eliminado. Los 12 tests de M0.01 se migraron a `spec/` (`requests/health_spec.rb`, `requests/ready_spec.rb`, `config/sidekiq_spec.rb`) y se añadieron `spec/services/readiness_check_spec.rb`, `spec/config/factory_bot_spec.rb` y `spec/config/audit_ignores_spec.rb`. Total: **27 ejemplos, 0 fallos**.
- **Pendientes de la revisión de M0.01:** (a) PostgreSQL que conecta bien pero cuyo `SELECT 1` se cuelga → 503 en menos de 3 s y `close` llamado; (b) "no usa el pool" ahora espía `checkout`, `with_connection` y `lease_connection` del pool de Active Record (con un control positivo que demuestra que el espía detecta un uso real). Verificado con mutaciones: quitar el `Timeout` rompe (a); quitar el `close` rompe (a) y el test de cierre; sustituir la conexión efímera por `ActiveRecord::Base.with_connection` rompe (b).
- **RuboCop** (`rubocop-rails-omakase` como base + `rubocop-rails`, `rubocop-rspec`, `rubocop-factory_bot`; decisión en `12-testing-strategy`), **brakeman 8.1** y **bundler-audit 0.9** (con `.bundler-audit.yml` y política de ignorados con fecha y motivo verificada por un spec). 0 ofensas, 0 avisos, 0 vulnerabilidades.
- **Frontend:** `frontend/packages/config` (`@ceiba/config`) con ESLint 10 (flat config), Prettier 3.9, `tsconfig.base.json` más estricto que el de M0.01 (`noImplicitOverride`, `noUnusedLocals`, ...) y Vitest con 15 tests de la propia configuración; apps con `extends` a ese tsconfig. Scripts de raíz `lint`, `format`, `format:check`, `typecheck`, `test`.
- **CI:** `.github/workflows/ci.yml` (6 jobs en paralelo), `pr-title.yml`, `dependabot.yml` (mensual: bundler, npm, github-actions), `pull_request_template.md`. Acciones fijadas por SHA. Validado con `actionlint` 1.7.12 (imagen Docker): atrapó un error real de YAML (un `name:` con dos puntos) antes de entregar.
- **`bin/ci` / `make ci`:** ejecuta en Docker los mismos `backend/bin/ci-*` y `frontend/bin/ci-*` que el workflow, más dos etapas solo locales (`repo-checks`, `workflows`). Acepta etapas como argumento.
- **`make hmr-check` ya no es intermitente:** `infra/scripts/hmr-check.mjs` pide `App.tsx` al proxy antes de editar (para que entre en el grafo de Vite) y reintenta una vez. 3 ejecuciones seguidas + 2 tras reiniciar `panel` y `booking` en frío: todas en verde.

Los nombres de los checks requeridos deben coincidir con los jobs la primera vez que se ejecuten.

Comprobar cómo calcula Dependabot el salto mayor con dos versiones en el mismo workspace (si evalúa por paquete, si el `ignore` `>=6.1.0 <7.0.0` + `semver-major` bloquea 6.0.3 -> 7.x en `packages/config` sin frenar 7.0.x en las apps) y ajustar `dependabot.yml` si no.
