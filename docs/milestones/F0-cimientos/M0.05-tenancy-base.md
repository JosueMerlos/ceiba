## Objetivo

Existen **Organización → Empresa → Sucursal** como modelos del pack `platform/tenancy`. Toda consulta a una tabla tenant **falla si no hay organización activa**. Una suite automática demuestra que la organización A nunca ve datos de la organización B, y se crea un tenant completo con **un único servicio de provisión**.

## Contexto

- Es la frontera más importante del sistema: un fallo aquí es una **fuga de datos entre clientes**, el peor incidente posible para un SaaS. Por eso va antes que la autenticación: la autenticación se construye **sobre** un tenancy ya probado.
- Decisiones que lo condicionan:
  - El tenant de `acts_as_tenant` es la **organización**. Empresa y sucursal son alcances de **autorización** (M0.08), no tenants.
  - RLS **preparado** desde el día 0 y activado en M4.03: cada tabla tenant ya nace con `organization_id` y la política creada pero deshabilitada (helper de M0.04).
  - Mercado Nicaragua: zona horaria por defecto `America/Managua`; moneda por empresa `NIO` o `USD`.
- El **servicio de provisión** es la pieza que hace "fácil afiliar organizaciones": seeds, back-office (M4.01), tests y el futuro auto-registro usan **el mismo** camino. Si cada uno crea tenants a su manera, cada uno termina con un estado inicial distinto.

## Alcance

**Incluye**

- Modelos y migraciones: `organizations`, `companies`, `branches`.
- `Current.context` (objeto inmutable) y su helper de bloque `Tenancy.with_context(...)`.
- Configuración de `acts_as_tenant` con `require_tenant = true`.
- `Tenancy::ProvisionOrganization` (API pública del pack).
- **Suite de aislamiento de tenant** genérica, que descubre automáticamente los modelos tenant.
- Seeds de demo: dos organizaciones con formas distintas.
- Validaciones de dominio: zona horaria IANA, moneda, slug.

**No incluye** (y dónde se resuelve)

- Usuarios, sesiones ni resolución del contexto desde la request → M0.07.
- Roles, memberships y autorización por empresa/sucursal → M0.08. (Aquí **no** se prueba que la empresa A no vea a la B dentro de la misma organización: eso es autorización, no tenancy.)
- `company_modules` y activación por defecto de `appointments` → M0.09 (el servicio de provisión expone un punto de extensión para ello).
- Branding (logo, colores) → M2.04.
- Activación de RLS → M4.03.

## Diseño

**Tablas** (todas con PK `uuid` por defecto `uuidv7()`; las tenant se crean con `create_tenant_table`):

```
organizations                     ← raíz del tenant (NO lleva organization_id)
  id, name, legal_name, country_code ('NI'), status (active|suspended), created_at, updated_at

companies                         ← tabla tenant
  id, organization_id, name, slug (único global), business_type (texto libre: 'salon', 'dental'…),
  currency ('NIO'|'USD'), locale ('es-NI'), status, timestamps
  UNIQUE (organization_id, id)    ← destino de las FKs compuestas

branches                          ← tabla tenant
  id, organization_id, company_id, name, time_zone (IANA, default 'America/Managua'),
  address, phone_e164, status, timestamps
  FK (organization_id, company_id) → companies (organization_id, id)
  UNIQUE (organization_id, id)
```

- `slug` es **único global** porque la URL pública es `/c/:slug`. Validación de formato `[a-z0-9-]{3,40}` y lista de **slugs reservados** (`api`, `admin`, `app`, `c`, `www`, `help`, …).
- `business_type` es **configuración**, no un módulo (ADR: el giro no es un módulo).
- `time_zone` se valida contra `ActiveSupport::TimeZone` / tzinfo; un valor inválido es un error de validación, no un crash en tiempo de ejecución.

**Contexto:**

```ruby
Current.context  # => Tenancy::Context(organization:, company: nil, branch: nil, principal: nil)
Tenancy.with_context(organization: org, company: co) { ... }  # fija el tenant de acts_as_tenant y el SET LOCAL de RLS
```

- `Context` es inmutable; cambiar de empresa crea un contexto nuevo.
- `with_context` es el **único** sitio que llama a `ActsAsTenant.with_tenant` y al `SET LOCAL app.organization_id`. Los jobs (M0.10) y las requests (M0.07) lo reutilizan.
- Valida la coherencia: `company.organization_id == organization.id` y `branch.company_id == company.id`; si no, lanza `Tenancy::InconsistentContext`.

**Provisión:**

```ruby
result = Tenancy::ProvisionOrganization.call(
  organization: { name:, legal_name: },
  company:      { name:, slug:, business_type:, currency: },
  branch:       { name:, time_zone: }
)
result.organization / result.company / result.branch
```

- Una transacción; si algo falla, no queda nada a medias.
- Idempotente por slug: si el slug ya existe, devuelve un error de dominio, no una excepción de BD.
- Publica hooks `after_provision` (lista registrable) para que M0.08 (rol de dueño) y M0.09 (módulos por defecto) se enganchen **sin modificar** este servicio.

**Suite de aislamiento (`spec/platform/tenancy/isolation_spec.rb`):**

- Descubre los modelos tenant en tiempo de test: todos los `ApplicationRecord` cuya tabla tiene `organization_id`. Así, **cada modelo nuevo de cualquier pack queda cubierto sin escribir un test nuevo**.
- Para cada modelo verifica: (a) consultar sin tenant lanza `ActsAsTenant::Errors::NoTenantSet`; (b) con el tenant A, `count` no incluye registros de B; (c) un `find` de un id de B dentro de A lanza `RecordNotFound`.
- Requiere una factory por modelo tenant; si falta, el test **falla** con un mensaje explícito ("agrega una factory para X"), en lugar de saltarse el modelo.

## Criterios de aceptación

1. **Dado** que no hay tenant activo, **cuando** se ejecuta `Company.count`, **entonces** se lanza `ActsAsTenant::Errors::NoTenantSet`.
2. **Dado** el contexto de la organización A, **cuando** se busca por id una empresa de la organización B, **entonces** se obtiene `RecordNotFound`.
3. **Dado** una sucursal, **cuando** se intenta asignarle una empresa de otra organización (incluso saltándose la validación del modelo con `update_columns`), **entonces** la **base de datos** rechaza la escritura por la FK compuesta.
4. **Dado** un nuevo modelo tenant agregado en cualquier pack sin factory, **cuando** corre la suite de aislamiento, **entonces** falla indicando qué factory falta.
5. **Dado** datos válidos, **cuando** se llama a `ProvisionOrganization`, **entonces** se crean la organización, la empresa y la sucursal en una transacción y se ejecutan los hooks registrados.
6. **Dado** un fallo en la creación de la sucursal, **cuando** se llama a `ProvisionOrganization`, **entonces** no queda ninguna organización ni empresa creada.
7. **Dado** el slug `admin` o uno ya usado, **cuando** se intenta provisionar, **entonces** se obtiene un error de dominio legible y no una excepción de BD.
8. **Dado** `time_zone: "Managua"` (no IANA), **cuando** se crea una sucursal, **entonces** la validación falla; con `America/Managua`, pasa.
9. **Dado** un contexto con una sucursal que no pertenece a la empresa indicada, **cuando** se llama a `with_context`, **entonces** se lanza `Tenancy::InconsistentContext`.
10. **Dado** una BD vacía, **cuando** se ejecuta `bin/rails db:seed` dos veces, **entonces** existen exactamente las 2 organizaciones de demo (los seeds son idempotentes).

## Riesgos y notas

| Riesgo | Mitigación |
| --- | --- |
| Que alguien use `ActsAsTenant.without_tenant` o `unscoped` "para salir del paso" | Regla de RuboCop custom (o grep en CI) que prohíba ambos fuera de una lista de archivos permitidos (reportes consolidados, back-office) |
| Que la suite de aislamiento no detecte un modelo nuevo | El descubrimiento se basa en la columna `organization_id`, no en una lista manual |
| Que la FK compuesta complique las factories | Factories que derivan `organization_id` del padre (`company.organization_id`), nunca uno independiente |
| Confundir tenancy con autorización de empresa | Explícitamente fuera de alcance; cubierto por la matriz de autorización de M0.08 |
