## Objetivo

En una máquina que solo tiene Docker y Git, **un único comando** levanta todo el ecosistema de desarrollo, y `http://localhost:8080` sirve la API, el panel y la página de reservas **desde el mismo origen**.

## Contexto

- Es el primer ladrillo: todo hito posterior asume que el entorno es reproducible. Si "en mi máquina funciona" aparece aquí, se arrastra durante meses.
- Se decidió **monorepo** (backend + frontend + infra + docs) para que un cambio de contrato API y su consumidor viajen en el mismo commit.
- Se decidió **mismo origen** (proxy que enruta por ruta) para que la cookie de sesión `httpOnly`, el CSRF y la ausencia de CORS funcionen en desarrollo **exactamente igual** que en producción. Probar con orígenes distintos en dev y uno solo en prod es la receta clásica de bugs de cookies que solo aparecen al desplegar.
- PostgreSQL **18** es obligatorio desde el primer día: los IDs serán `uuidv7()` nativo (M0.04).

## Alcance

**Incluye**

- Estructura del monorepo:
  ```
  backend/            Rails 8 en modo API (vacío salvo /health)
  frontend/           pnpm workspace
    apps/panel        Vite + React + TS (página placeholder)
    apps/booking      Vite + React + TS (página placeholder)
    packages/         (vacío, con .gitkeep)
  infra/
    docker/           Dockerfiles de desarrollo
    proxy/            configuración del proxy de desarrollo
  docs/
  compose.yaml
  Makefile            atajos: up, down, logs, sh-api, console, reset-db
  .tool-versions      versiones fijadas (referencia para quien no use Docker)
  ```
- Servicios en `compose.yaml`: `db` (PostgreSQL 18), `redis`, `api` (Rails), `worker` (Sidekiq), `panel` (Vite dev server), `booking` (Vite dev server), `mailpit` y `proxy`.
- Proxy de desarrollo (Caddy) en el puerto `8080`:
  - `/api/*` → `api`
  - `/c/*` → `booking`
  - `/*` → `panel`
  - Con HMR de Vite funcionando a través del proxy (websocket).
- Endpoint `GET /api/health` → `200 {"status":"ok"}`, sin tocar la BD, y `GET /api/ready` → `200` solo si PostgreSQL y Redis responden.
- Volúmenes con nombre para la BD y las dependencias (gems, `node_modules`) para que los reinicios sean rápidos.
- `README.md` raíz con requisitos, comando de arranque, URLs de cada servicio y solución de problemas comunes.
- Inicializar git con `.gitignore` y `.editorconfig`.

**No incluye** (y dónde se resuelve)

- CI y linters → M0.02.
- Packwerk y estructura de packs → M0.03.
- Configuración de la base de datos (UUIDv7, helpers) → M0.04.
- Imagen de producción multi-etapa, Kamal y proxy de producción → M4.04.
- Cualquier modelo o funcionalidad de negocio.

## Diseño

- **Versiones fijadas** en los Dockerfiles y en `.tool-versions`: Ruby 3.4.x, Rails 8.x, Node LTS vigente, pnpm, PostgreSQL 18, Redis 7+. Al implementar, verificar la última versión estable de cada uno y fijar la exacta, nunca `latest`.
- `rails new backend --api --database=postgresql --skip-test` (RSpec entra en M0.02); se mantienen los defaults de Rails 8 salvo los que contradigan los ADRs (Solid Queue **no** se usa: los jobs van en Sidekiq).
- El usuario de los contenedores no es root y coincide en UID con el host, para evitar archivos con dueño `root` en el repo.
- Variables de entorno en `.env.example` (versionado) → `.env` (ignorado). Ningún secreto real en el repo.
- `healthcheck` en `db` y `redis`; `api` y `worker` arrancan con `depends_on: condition: service_healthy`.
- `bin/setup` dentro de `api` es idempotente: crea la BD si no existe y corre migraciones. Lo invoca el arranque.

## Criterios de aceptación

1. **Dado** un clon limpio del repo en una máquina con solo Docker y Git, **cuando** se ejecuta `make up` (o `docker compose up`), **entonces** todos los servicios llegan a estado `healthy`/`running` sin pasos manuales adicionales.
2. **Dado** el entorno levantado, **cuando** se pide `GET http://localhost:8080/api/health`, **entonces** responde `200` con `{"status":"ok"}`.
3. **Dado** el entorno levantado con Redis detenido, **cuando** se pide `GET /api/ready`, **entonces** responde `503`; al volver Redis responde `200`.
4. **Dado** el entorno levantado, **cuando** se abre `http://localhost:8080/`, **entonces** se ve el placeholder del **panel**, y en `http://localhost:8080/c/demo` el placeholder de **booking**: el mismo puerto y el mismo origen.
5. **Dado** el panel abierto en el navegador, **cuando** se edita un componente en `apps/panel`, **entonces** el cambio se refleja sin recargar manualmente (HMR a través del proxy).
6. **Dado** el entorno levantado, **cuando** se abre la UI de Mailpit, **entonces** es accesible en la URL documentada en el README.
7. **Dado** que se ejecutó `docker compose down` (sin `-v`), **cuando** se vuelve a levantar, **entonces** los datos de PostgreSQL persisten y el arranque no reinstala dependencias.
8. **Dado** un archivo creado desde un contenedor, **cuando** se inspecciona en el host, **entonces** su dueño es el usuario del host, no `root`.

## Riesgos y notas

| Riesgo | Mitigación |
| --- | --- |
| HMR de Vite no funciona tras el proxy (websocket) | Configurar `server.hmr.clientPort = 8080` en Vite y el upgrade de websocket en Caddy; está en los criterios de aceptación para no descubrirlo tarde |
| `bundle install` / `pnpm install` lentos en cada arranque (en macOS sobre todo) | Volúmenes con nombre para gems y `node_modules`; no montar `node_modules` del host |
| Archivos con dueño `root` en el repo | UID/GID del host pasados como build args |
| Elegir versiones "latest" que luego rompen | Versiones exactas fijadas y documentadas |

### Evidencias y comandos reproducibles

| Criterio | Evidencia |
| --- | --- |
| 1. `make up` sin pasos manuales | Clon limpio, `docker compose down -v` y `make up`: los 8 servicios `healthy`/`running` (el `worker` no define healthcheck: `running`) |
| 2. `/api/health` | `test/integration/health_test.rb` (200, `{"status":"ok"}`, cero consultas SQL, ruta solo bajo `/api`) y `make smoke` a través del proxy |
| 3. `/api/ready` con Redis detenido | `test/integration/ready_test.rb` (503 con Redis o PostgreSQL caídos, o aceptando la conexión sin responder nunca —servidor TCP "agujero negro"— en menos de 3 s; sin filtrar detalles ni tocar el pool de AR) y a mano: `docker compose stop redis` → `503` (1 s la primera vez por el timeout, ~30 ms después) → `docker compose start redis` → `200` |
| 4. Placeholders en `/` y `/c/demo` | `make smoke` (mismo puerto 8080) |
| 5. HMR a través del proxy | `./infra/scripts/hmr-check.sh`: abre el websocket `vite-hmr` por `proxy:8080` (101), edita `App.tsx` y recibe el mensaje `update`, para panel y booking. No se probó con un navegador real |
| 6. Mailpit | `make smoke` → `http://localhost:8025` 200 |
| 7. Persistencia | Se insertó una fila, `docker compose down` (sin `-v`), `up`: la fila sigue ahí; el segundo arranque tardó 17.5 s y no instaló nada (`bundle check` satisfecho; pnpm "Done in 1.2s") |
| 8. Dueño de archivos | Desde el contenedor (`uid=501(app) gid=20`): `Gemfile.lock`, `pnpm-lock.yaml` y archivos creados con `touch` son `501:20` en el host. El GID 20 ya existe en la imagen (`dialout`); `groupadd --non-unique` lo resuelve |

Resistencia a PostgreSQL colgado (`docker compose pause db`): 4 peticiones concurrentes a `/api/ready` responden 503 en ~1-2 s y `/api/health` sigue en 200; tras `unpause`, `/api/ready` vuelve a 200.

Suite completa: `make test` (o `docker compose exec api bin/rails test && docker compose exec -w /app/frontend panel pnpm -r test`) → backend `12 runs, 27 assertions, 0 failures, 0 errors`; frontend `2 test files, 2 tests passed`.

### Tiempos

Validación en limpio (clon del repo en otro directorio, `COMPOSE_PROJECT_NAME=ceiba_clean`, `docker compose down -v`, volúmenes inexistentes): **62 s** desde `docker compose build --no-cache` hasta todos los servicios `healthy`, en macOS arm64 con Docker 27.5. Las imágenes base (ruby, node, postgres, redis, caddy, mailpit) ya estaban descargadas: en una máquina totalmente fría hay que sumar su descarga (~700 MB). Arranque en caliente (`down` + `up`): 17.5 s.

### Limitaciones y pendientes

- **`.env.example`**: crear en la raíz con `PROXY_PORT`, `MAILPIT_PORT`, `HOST_UID`, `HOST_GID`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `REDIS_URL` y `RAILS_ENV` (mismos valores por defecto que `compose.yaml`) y volver a enlazarlo desde el README.
- Los nodos `node_modules` (raíz y por app) son volúmenes con nombre montados dentro del bind mount de `frontend/`; en Linux Docker puede crear los directorios vacíos del punto de montaje con dueño root en el host (están en `.gitignore`; en macOS no ocurre).
- El HMR se verificó a nivel de protocolo; falta una comprobación visual en navegador.
- Con un UID distinto de 1000 en Linux, `docker compose up` directo (sin `make`) construye con 1000: usar `make up` o exportar `HOST_UID`/`HOST_GID`.
- Sin remoto GitHub: nada de este hito depende de él.
